# 카페 운영 기록 웹 프로그램 1차 개발계획

- 확정일: 2026-10-12
- 상태: **EPIC 1~3 / S01~S14 개발·검수 완료**. EPIC 1은 사용자 직접 확인, EPIC 2·3은 2026-10-12 사용자의 검수 위임에 따라 에이전트가 검수했다. GitHub 보관·실제 Vercel 배포는 별도 마무리 작업으로 남아 있다.
- 기준: [PRD](01_PRD.md), [FRD](02_FRD.md), [TRD](03_TRD.md), `design` 폴더의 시안.
- EPIC은 관련 작업을 모은 묶음, User Story는 사용자가 한 가지 목적을 달성하는 기능 단위다.

## 1. 전체 순서와 개수

**판매부터 결과 확인 → 운영 기록 보완 → 엑셀·백업·복원 → 최종 검사·배포 순서로 진행한다. 1차는 EPIC 3개, Story 총 14개다.**

| 순서 | 작업 묶음 | Story 수 | 실제 화면에서 확인할 결과 |
| --- | --- | ---: | --- |
| 1 | EPIC 1. 판매를 기록하고 수익·잔량 확인하기 | 5 | 판매 입력이 메뉴 수익성·기간 손익·재료 잔량으로 연결됨 |
| 2 | EPIC 2. 비용과 재고를 관리하고 기록 바로잡기 | 5 | 비용·입고·폐기·실사가 반영되고 잘못된 판매를 수정할 수 있음 |
| 3 | EPIC 3. 엑셀로 기록하고 백업으로 복구하기 | 4 | 실제 엑셀 파일을 가져오고 백업 시점으로 복원할 수 있음 |
| 마무리 | 전체 검사·GitHub 보관·Vercel 배포 | 별도 Story 없음 | 운영 주소에서도 저장·파일·핵심 흐름이 정상 작동함 |

먼저 핵심 흐름을 완성하고, 그 위에 기록 변경과 파일 처리를 붙인다. 엑셀 가져오기는 직접 입력의 검사·계산·저장 기능을 재사용하고, 복원은 모든 기록 구조가 갖춰진 뒤 검증한다.

화면 틀·공통 계산·저장 기반은 각 Story에 필요한 구현 작업으로 포함한다. 사용자 목적이 다른 입고·폐기·실사와 백업·복원은 각각 나눈다. 비용의 추가·수정·삭제는 같은 비용 장부를 관리하는 작은 기능으로 묶는다.

## 2. EPIC 1. 판매를 기록하고 수익·잔량 확인하기

**포함 Story: S01~S05, 총 5개**

**완료 기준:** 가상 샘플로 시작해 판매를 실제 저장하고, 같은 기록을 근거로 메뉴 수익성·일/월 손익·재료 잔량을 확인한다. 프로그램을 다시 열어도 기록이 유지된다. 비용은 이 단계에서 제공된 비용기록을 사용한다.

### S01. 제공 자료로 시작하고 기록을 이어서 보기

- **사용자가 할 수 있는 일:** 처음에는 가상 샘플로 시작하고, 다음에는 같은 브라우저에 저장된 기록을 이어서 연다.
- **자동 검사:** 초기 자료의 개수·ID·연결 관계 검사, 재실행 시 중복 초기화 방지, 손상된 저장 자료의 자동 덮어쓰기 방지, 유효한 빈 복원 상태 보존.
- **직접 확인할 행동과 예상 결과:** 첫 실행에서 메뉴 8개·재료 11개와 기록 기간을 확인한다. 다시 열었을 때 판매 6,112건 등 샘플이 두 배로 늘지 않아야 한다.
- **연결과 의존성:** FRD F01·F15. 이후 모든 Story의 기반이다.

### S02. 하루의 메뉴·채널별 판매를 기록하기

- **사용자가 할 수 있는 일:** 날짜·메뉴·매장/포장·수량·실제 단가·할인·전체 수수료를 입력하고 미리보기를 확인한 뒤 저장한다.
- **자동 검사:** 순매출·적용일 원가·포장 원가·수수료 계산, 필수값 누락·할인 초과·판매 중복 차단, 연속 클릭 중복 방지, 저장 실패 시 기존 자료 유지.
- **직접 확인할 행동과 예상 결과:** 기록이 없는 날짜에 5,000원 메뉴 10개, 할인 2,000원, 수수료 1,200원을 입력한다. 순매출은 **48,000원**이어야 한다. 저장 후 다시 열어도 같은 기록이 남고, 수수료 공란은 오류로 안내해야 한다.
- **연결과 의존성:** F02·F03·F15. S01 이후 진행한다.

### S03. 메뉴가 직접 남기는 이익 확인하기

- **사용자가 할 수 있는 일:** 기간·채널·분류를 선택해 메뉴별 판매량·직접비·공헌이익을 비교하고 레시피 근거를 읽는다.
- **자동 검사:** 당시 원가 보존, 포장 채널 적용, 합계 기준 이익률, 원화·비율 반올림, 순매출 0·원가 누락 처리. 임차료·인건비가 메뉴에 배분되지 않는지 확인한다.
- **직접 확인할 행동과 예상 결과:** S02의 판매 기간·채널을 선택한다. 순매출 48,000원과 저장 당시 원가·수수료를 사용한 이익이 보여야 한다. 채널을 바꾸면 해당 기록만 조회되고, 레시피 수정 기능은 없어야 한다.
- **연결과 의존성:** F07. S02의 확정 판매·원가를 사용한다.

### S04. 일·월 매출과 운영 손익 확인하기

- **사용자가 할 수 있는 일:** 날짜 또는 월을 선택해 순매출·직접비·수수료·기타 비용·운영 손익을 확인한다.
- **자동 검사:** 일별 비용만 합산, 월계획·입고 대금 중복 차감 방지, 비용만 있는 날 포함, 마감·미마감·자료 없음 구별, 정렬·펼치기에 따른 합계 불변.
- **직접 확인할 행동과 예상 결과:** S02의 판매일과 해당 월을 조회한다. 판매가 반영되어야 하고, 미마감 날짜는 확정 실적과 구별되어야 한다. 월계획이 같은 비용으로 다시 차감되면 안 된다.
- **연결과 의존성:** F08. S02 이후 진행하며, 비용 직접 관리는 S07에서 연결한다.

### S05. 판매에 따른 재료 잔량과 부족 재료 확인하기

- **사용자가 할 수 있는 일:** 기준일별 재료 잔량을 보고 재료명·공급사로 검색하며 부족·확인 대상을 찾는다.
- **자동 검사:** 초기재고·입고·폐기·판매 사용량·기존 실사 반영, 포장재 사용량, 기준일 이후 기록 제외, 잔량 0 이하 표시, 누락 자료의 계산 불가 표시.
- **직접 확인할 행동과 예상 결과:** 같은 기준일의 잔량을 비교한다. 아메리카노 포장 판매 10개를 추가했다면 원두 사용량 **200g**, 포장컵세트 사용량 **10개**가 반영되어야 한다. 양수 잔량을 ‘향후 충분함’으로 표시하지 않아야 한다.
- **연결과 의존성:** F09. S02와 초기 재고·기존 실사 자료를 사용한다.

## 3. EPIC 2. 비용과 재고를 관리하고 기록 바로잡기

**포함 Story: S06~S10, 총 5개**

**완료 기준:** 판매 수정·삭제와 비용 관리가 손익에 반영되고, 입고·폐기·실사가 재료 잔량에 정확히 연결된다. 실패·취소·다른 탭의 변경으로 기록이 일부만 저장되거나 덮어써지지 않는다.

### S06. 잘못된 판매 기록 바로잡기

- **사용자가 할 수 있는 일:** 기존 판매를 수정하거나 삭제한다.
- **자동 검사:** 수량 변경 시 개당 원가 유지, 날짜·메뉴·채널 변경 시 원가 재검사, 수정 대상 충돌 방지, 삭제 후 사용량 제거, 실사 이전 수정 시 실측값 보존.
- **직접 확인할 행동과 예상 결과:** 판매량을 10개에서 12개로 바꾸면 판매·이익·재료 사용량이 함께 바뀌어야 한다. 삭제하면 해당 판매와 사용량이 제거되고, 취소하면 그대로 남아야 한다.
- **연결과 의존성:** F04. S02~S05 이후 진행한다.

### S07. 기간 비용 장부 관리하기

- **사용자가 할 수 있는 일:** 비용의 귀속일·항목·금액을 기록하고 잘못된 비용을 수정·삭제한다.
- **자동 검사:** 금액·날짜·항목 검사, 중복 가능성 확인, 선택한 ID만 수정·삭제, 귀속일 변경에 따른 기간 손익 갱신, 월계획 재생성 방지.
- **직접 확인할 행동과 예상 결과:** 비용 10,000원을 추가하면 해당 기간 손익이 10,000원 줄어야 한다. 귀속일을 다른 달로 바꾸면 두 달의 비용·손익이 각각 바뀌고, 삭제하면 해당 비용만 제거되어야 한다.
- **연결과 의존성:** F05·F06. S04의 손익 계산·화면을 재사용한다.

### S08. 재료 입고 기록하기

- **사용자가 할 수 있는 일:** 재료·입고일·기준단위 수량·공급사 등을 기록한다.
- **자동 검사:** 단위·수량·연결 대상 검사, 저장과 잔량 동시 반영, 입고 대금의 손익 비용 자동 생성 방지, 과거 판매 원가 변경 방지.
- **직접 확인할 행동과 예상 결과:** 최근 실사 이후 날짜에 원두 1,000g을 입고하면 해당 시점 이후 잔량이 1,000g 늘어야 한다. 기간 비용과 과거 판매 원가는 바뀌지 않아야 한다.
- **연결과 의존성:** F10. S05 이후 진행한다.

### S09. 재료 폐기 기록하기

- **사용자가 할 수 있는 일:** 재료·폐기일·폐기량·사유를 기록한다.
- **자동 검사:** 양수 입력을 음의 재고 변화로 한 번만 반영, 단위·사유 검사, 음수 잔량 경고, 실패 시 이전 상태 유지.
- **직접 확인할 행동과 예상 결과:** 원두 100g 폐기 후 잔량이 100g 줄어야 한다. 부족량을 넘겨 폐기하면 경고와 음수 잔량이 보여야 한다. 폐기 평가금액을 손익에서 추가 차감하지 않아야 한다.
- **연결과 의존성:** F11. S05 이후 진행한다.

### S10. 실제 센 재고를 기준으로 맞추기

- **사용자가 할 수 있는 일:** 실사일의 실제 수량과 사유를 입력하고 차이를 확인한 뒤 확정한다.
- **자동 검사:** 실사 직전 잔량과의 차이, 같은 날 중복 실사 차단, 확인란·음수 입력 검사, 다음 날부터 변화 반영, 기존 실사조정 이중 합산 방지.
- **직접 확인할 행동과 예상 결과:** 독립 검사 자료에서 장부 2,450g을 실측 2,100g으로 확정하면 차이는 **−350g**이어야 한다. 다음 날 입고 1,000g·판매 사용 500g이면 잔량은 **2,600g**이다. 실사 이전 판매를 고쳐도 실측 2,100g 자체는 유지되어야 한다.
- **연결과 의존성:** F12. S05·S06·S08·S09를 연결해 확인한다.

## 4. EPIC 3. 엑셀로 기록하고 백업으로 복구하기

**포함 Story: S11~S14, 총 4개**

**완료 기준:** 실제로 내려받은 양식에 작성한 판매·비용을 가져올 수 있다. 전체 기록을 백업하고 복원한 뒤 다시 열어도 결과가 일치한다. 오류 파일은 일부만 반영하지 않는다.

### S11. 엑셀로 판매 기록 가져오기

- **사용자가 할 수 있는 일:** 판매 양식을 내려받아 작성하고, 검사 결과를 확인한 뒤 가져온다.
- **자동 검사:** 생성 양식 재읽기, 필수 열·날짜·숫자·수식·메뉴·원가 검사, 기존/파일 내부 중복·충돌, 오류 시 전체 미반영, 확정 전 다른 탭 변경 검사.
- **직접 확인할 행동과 예상 결과:** 양식에 새 판매를 작성해 가져오면 목록·수익성·손익·잔량이 직접 입력과 동일하게 바뀌어야 한다. 같은 파일을 다시 가져오면 같은 판매가 추가되지 않아야 한다. 오류 행 하나를 섞으면 전체가 반영되지 않아야 한다.
- **연결과 의존성:** F13·F14의 판매 부분. 직접 입력·계산·저장 기능 이후 진행한다.

### S12. 엑셀로 비용 기록 가져오기

- **사용자가 할 수 있는 일:** 비용 양식을 내려받아 작성하고 검사 후 가져온다.
- **자동 검사:** 귀속일·항목·금액 검사, ID 충돌, ID 없는 동일 비용의 식별 불가 오류, 전체 반영/실패, 판매 양식과 대상 구별.
- **직접 확인할 행동과 예상 결과:** 새 비용을 가져오면 해당 기간 비용·손익이 바뀌고 재고는 그대로여야 한다. ID 없이 기존과 날짜·항목·금액이 같은 비용은 자동 추가하지 않고 이유를 안내해야 한다.
- **연결과 의존성:** F13·F14의 비용 부분. S07과 S11의 공통 파일 처리 기반을 사용한다.

### S13. 전체 기록을 백업 파일로 보관하기

- **사용자가 할 수 있는 일:** 마지막 저장 상태 전체를 JSON 백업 파일로 내려받는다.
- **자동 검사:** 판매·비용·재고·실측값·기준 자료·마감 상태·버전 포함, 같은 저장 상태에서 파일 생성, 미저장 입력 제외, 파일 생성 실패 처리.
- **직접 확인할 행동과 예상 결과:** 백업을 실행해 실제 파일이 내려받아지는지 확인한다. 입력창에만 작성한 값은 포함되지 않고, 화면에 마지막 저장 상태의 백업임이 안내되어야 한다.
- **연결과 의존성:** F16. S01~S10의 저장 자료 구조를 포함한다.

### S14. 백업 시점으로 전체 기록 복원하기

- **사용자가 할 수 있는 일:** 백업 파일을 검사하고 전체 교체를 확인해 이전 상태로 돌아간다.
- **자동 검사:** 구조·버전·ID·참조 검사, 취소·손상·미지원 버전의 기존 자료 보존, 전체 교체, 오래된 탭 저장 차단, 복원 후 재계산, 유효한 빈 백업 처리.
- **직접 확인할 행동과 예상 결과:** 백업 후 판매·비용·재고를 변경하고 복원한다. 모든 기록과 결과가 백업 시점으로 돌아가고, 다시 열어도 유지되어야 한다. 손상 파일을 선택하면 기존 기록은 그대로 남아야 한다.
- **연결과 의존성:** F17. S13 이후 모든 기록 종류를 함께 검증한다.

## 5. 모든 Story에 적용할 완료 기준

각 Story는 다음을 모두 충족해야 완료로 표시한다.

- 실제 기록으로 작동하며 확정 변경이 브라우저 저장소에 남는다.
- 관련 계산·화면 결과가 같은 저장 상태를 기준으로 일치한다.
- 필수값·누락 자료·취소·저장 실패 등 해당 기능의 오류 처리가 작동한다.
- 자동 검사가 통과하고 실제 브라우저에서 정해진 행동을 확인한다.
- 구현 완료, 자동 검사 통과, 사용자 직접 확인 또는 명시적으로 위임받은 검수 상태를 따로 기록한다. 위임 검수를 사용자의 직접 관찰로 기록하지 않는다.

계산은 FRD C01~C07을 그대로 사용한다. 자동 검사는 Vitest로 계산을, Playwright와 실제 IndexedDB로 저장·화면·파일 흐름을 확인한다. 사용자 화면 확인이 자동 검사를 대신하지 않는다. 화면만 만들거나 가짜 성공 알림으로 완료 처리하지 않는다.

화면 예시는 검사할 조건을 설명한 것으로 실제 샘플의 전체 합계라는 뜻이 아니다. 판매 입력 검사는 기존 기록과 겹치지 않는 날짜·메뉴·채널을 사용하고, 재고 증감 검사는 이후 실사가 없는 기준일에서 전후 값을 비교한다. S10의 숫자는 독립 검사 자료로 확인한다.

## 6. 최종 검사·배포와 범위 확인

14개 Story 이후에는 다음을 별도 마무리 작업으로 수행한다. 사용자 기능 Story 개수에는 추가하지 않지만 완료에 필요한 작업이다.

- FRD V01~V17 전체 연결 검사와 TRD의 성능·개인정보·배포 검사.
- 입력 파일과 실제 매장 기록이 외부로 전송되지 않는지 확인.
- GitHub에 코드·문서·검사 결과 보관. 실제 영업자료·백업·비밀값은 제외.
- Vercel 미리보기 확인 후 운영 배포, 고정 주소에서 재실행·기록 보존·파일 처리 확인.

PRD의 **기획 25분·화면 설계 20분·개발 140분·검사 40분·배포 15분, 총 240분 목표**를 유지한다. 시간 부족을 이유로 계산·저장·오류 검사나 필수 기능을 빼고 완료 처리하지 않는다. 4시간은 목표이며, 실제 지연·미완료 항목은 따로 알린다.

예상 손익·발주량 추천·주/분기/반기/연간 조회 등은 기존 문서대로 2차에 남긴다. 시안의 리포트 내보내기·감사 로그·원가 변동 시뮬레이션 등 추가 기능도 이번 계획에 넣지 않는다.
