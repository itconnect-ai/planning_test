# 카페 운영 기록 웹 프로그램 제품 요구사항 문서(PRD)

- 작성일: 2026-10-12
- 상태: 제품 요구사항 정리 완료. 2026-10-12 사용자 지시 “모두 추천으로 해줘”에 따라 추천 범위와 업무 기본안을 채택했다. 구현·검사·배포는 아직 진행하지 않았다.
- PRD는 누구의 어떤 문제를 해결하고 무엇을 제공할지 정하는 문서다.
- 이번 문서에서는 계산식, 화면 디자인, 기술 선택, 상세 동작, 코드를 정하지 않는다.

## 1. 제품의 목적

카페 운영자가 판매와 비용을 기록하고, 어떤 메뉴가 수익에 도움이 되는지, 선택한 기간의 실적과 손익이 어떤지, 재료가 얼마나 남았는지 한 흐름에서 확인하도록 돕는다.

전체 제품은 예상 손익과 필요한 발주량까지 참고할 수 있도록 확장한다. 1차 구현(MVP: 먼저 사용할 수 있는 최소 기능)은 **판매 기록 입력 → 메뉴 수익성 확인 → 기간 손익과 재료 잔량 확인**에 집중한다.

주요 사용자는 카페 운영자다. 1차는 한 매장·운영자 한 명이 같은 PC의 웹 브라우저에서 사용하는 범위로 정한다. 여러 기기 간 공유와 외부 접속은 1차에 포함하지 않는다. 이는 자료에서 확인한 사실이 아니라 사용자가 위임한 추천 기본안이다.

## 2. 자료에서 확인한 사실

### 2.1 확인한 자료와 범위

- 원본: [데이터 설명](../data/데이터설명.md), [엑셀](../data/매장운영데이터.xlsx), [JSON](../data/매장운영데이터.json).
- 직접 구성한 가상 매장인 ‘프렙 카페’의 샘플이다. 실제 영업 성과나 운영 정확성을 입증하는 자료가 아니다.
- 기록 시작일은 2025-07-01, 마감 기준일은 2026-09-18이다. 영업달력은 2026-09-30까지 있다.
- 금액은 원이며 부가세 제외 기준이다. 재료 수량은 g·ml·개로 기록되어 있다.
- 엑셀과 JSON은 같은 기록의 두 형식이다. 주요 11개 기록 묶음의 행 수와 항목별 값을 대조했으며 날짜 표현과 빈칸 표현을 맞추면 일치한다. 엑셀에는 안내·자료정보 시트도 있다.
- JSON의 `settings`는 비어 있다. 운영 정책이 이미 합의되어 있다고 볼 수 없다.

| 기록 | 수 | 확인된 내용과 쓰임 |

| 영업달력 | 457 | 영업·마감 여부, 날씨, 메모 |

### 2.3 기획할 때 주의할 점

1. **중복 집계:** 엑셀과 JSON을 별도 기록으로 더하지 않는다. 월비용계획과 비용기록도 같은 비용의 두 표현이므로 이중 지출로 보지 않는다.
2. **판매 기록의 의미:** 판매 한 행은 날짜·메뉴·채널별 집계다. 고객 주문 한 건이 아니므로 주문 건수나 고객 수를 알 수 없다.
3. **원가의 의미:** 구매가격은 구매용량 전체 가격이며, 판매 기록의 식재료·포장 원가는 한 개당 금액이다. 포장 재료의 적용채널과 단위도 구별해야 한다.
4. **과거와 현재의 구별:** 당시 판매가격·원가·수수료가 남아 있다. 자료만으로 과거 실적 변경 정책을 알 수 없다. 이번에 채택한 정책은 6장의 과거 기록 보존 기준을 따른다.
5. **기간의 구별:** 미래 미마감 날짜는 판매 0이 아니다. 연간·반기 등 자료가 일부만 있는 기간을 전체 기간 실적으로 오해하지 않도록 한다.
6. **재고의 구별:** 기록으로 파악한 잔량과 실제 세어 본 수량은 다를 수 있다. 입고, 폐기, 실사조정과 판매 사용량의 관계는 자료 자체의 합의 사항이 아니다. 이번에 채택한 업무 원칙은 6장에 구분해 기록한다. 납기·안전재고 일수는 영업일 기준이다.
7. **빈칸의 의미:** 미입력·해당 없음과 숫자 0을 구별해야 한다. 필요한 자료가 없는데 정상 결과인 것처럼 보여 주지 않는다.
8. **비용의 성격:** 제공된 비용은 월비용을 일별로 배분한 기록이다. 실제 현금 지출일을 기록한 내역으로 해석하지 않는다.

기초 점검에서 판매·재고·비용의 식별번호 중복은 없었고, 판매의 메뉴 연결과 레시피·재고의 재료 연결에서 없는 대상의 참조는 발견되지 않았다. 모든 계산 결과나 재고의 정확성을 검증했다는 뜻은 아니다.

## 4. 1차 구현 범위

### 4.1 4시간 계획의 전제

제공 자료의 메뉴·재료·레시피를 출발점으로 삼고, 한 매장의 핵심 흐름을 사용할 수 있는 첫 버전을 목표로 한다. 새 메뉴·재료·레시피를 자유롭게 구성하는 기능은 2차로 둔다.

4시간은 기획·화면 설계·개발·검사·배포를 모두 포함한 계획 예산이다. 소요 시간을 보장하는 확정 일정은 아니다. 1차 배포 완료는 선택한 PC의 브라우저에서 실행하고 핵심 흐름을 사용할 수 있는 상태를 뜻한다. 범위가 늘어나면 검사 시간을 없애지 않고 범위나 일정을 다시 협의한다.

### 4.2 핵심 기능과 완료 기준

아래 완료 기준은 제품 관점의 검사 목표다. 구현 순서나 버튼·창·파일 구조 등 상세 동작을 지정하지 않는다.

| 번호 | 1차 기능 | 사용자가 확인할 완료 기준 |
| --- | --- | --- |
| M01 | 제공 샘플 자료로 시작 | 제공 기록과 메뉴·재료의 연결을 유지하며, 같은 자료를 두 형식으로 중복 반영하지 않는다. |
| M02 | 판매 기록 입력·수정·삭제 | 날짜·메뉴·매장/포장별 판매 기록을 관리할 수 있고, 변경 내용이 관련 수익성·손익·재료 잔량에 일관되게 반영된다. |

| M06 | 재료 입고·폐기·실제 재고 기록과 잔량 확인 | 재료별 기록과 기준 시점의 잔량을 확인한다. 기록상 잔량과 실제로 센 수량을 구별하고, 부족하거나 확인이 필요한 재료를 파악한다. |

| M08 | 저장·백업·복원 | 프로그램을 다시 열어 기록을 이어서 사용하고, 백업으로 판매·비용·재고 기록과 결과 해석에 필요한 기준을 복원할 수 있다. |

부족 재료, 중복 기록, 저장·복원에 대한 업무 원칙은 6장의 채택 기준을 따른다. 실제 입력 방식, 오류 처리 절차, 저장 기술 등 상세 동작은 후속 설계에서 정한다.

### 4.3 핵심 사용 흐름

1. 제공 자료 또는 기존 저장 기록으로 시작한다.
2. 판매 기록을 직접 입력하거나 정해진 엑셀 양식으로 가져온다. 비용도 기록한다.
3. 같은 기간의 메뉴별 수익성을 확인한다.
4. 같은 기간의 매장 손익과 기준 시점의 재료 잔량을 확인한다.
5. 입고·폐기·실제 재고를 기록한 경우 잔량을 다시 확인한다.
6. 기록을 저장하고 필요할 때 백업·복원한다.

검사에서는 판매·비용 변경, 포장 판매, 재고 기록, 자료가 일부만 있는 기간, 백업 복원을 포함해 이 흐름이 이어지는지 확인한다. 정확한 기대 금액·수량은 후속 설계에서 계산 기준을 정한 다음 별도 검사 자료에 작성한다.

## 5. 2차 구현 범위

| 확장 기능 | 2차로 제안하는 이유 |
| --- | --- |
| 예상 손익 | 무엇을 얼마나 앞서 예상할지와 가정의 기준이 필요하다. 실제 실적과 구별해 제공한다. |
| 재료 부족 예상·발주량 참고 | 납기·안전재고·예상 사용량·구매용량에 대한 판단 기준이 필요하다. |
| 주·분기·반기·연간 조회 | 1차 일·월 조회가 검증된 뒤 확장한다. 월요일 시작 주간과 달력 기준 기간을 사용하며 자료가 일부인 기간을 구별한다. |
| 메뉴·재료·레시피·가격이력 관리 | 과거 기록에 미치는 영향까지 확인해야 한다. |

| 상세 비교·수익성 분류 | 좋은 메뉴·주의 메뉴 등의 구분은 사용 목적과 기준 합의가 필요하다. |

사용자가 요청한 예상 손익·발주량·모든 기간 조회는 2차에 포함한다. 2026-10-12 추천안 일괄 채택 지시에 따라 이 단계 구분을 확정했다. 자동 발주, 외부 판매·회계 서비스 연결, 세금 신고, 여러 매장 관리는 이번 범위에서 제외한다.

## 6. 채택한 추천 기준

2026-10-12 사용자가 D01에서 A를 선택했고, 이어서 “모두 추천으로 해줘”라고 지시했다. D02의 추천 범위를 채택하고 남은 업무 주제에는 아래 기본안을 적용한다. 아래 내용은 원본 데이터의 사실이 아니라 사용자 위임에 따라 정한 제품 요구사항이다. 추가 선택 질문 없이 이번 PRD를 마무리한다.

| 번호 | 주제 | 채택 기준 | 쉬운 예시와 추천 이유 |
| --- | --- | --- | --- |
| D01 | 메뉴 수익성 | 재료·포장·결제수수료 등 직접 드는 비용 중심으로 본다. 임차료·인건비는 매장 전체 손익에서 확인한다. | 아메리카노가 매장 수익에 얼마나 기여하는지 비교한다. 공통비를 메뉴에 나누는 작업을 줄인다. |
| D02 | 구현 단계 | 1차는 M01~M08, 2차는 5장의 확장 기능으로 구분한다. | 먼저 판매 입력부터 손익·재료 잔량까지 연결해 검사한다. 4시간 목표에 집중한다. |
| D03 | 이용 환경 | 한 매장·운영자 한 명·같은 PC의 브라우저 사용을 기준으로 한다. | 매장 PC에서 기록을 이어 쓴다. 계정·권한·기기 간 공유 기능을 줄인다. |
| D04 | 과거 기록과 새 판매 | 이미 저장된 당시 가격·원가·수수료는 보존한다. 새 판매는 판매일에 해당하는 가격이력과 레시피를 기준으로 하며, 수수료 등 확인할 수 없는 필수 금액은 입력이 필요함을 알린다. | 오늘 우유 가격이 바뀌어도 지난달 라테의 당시 원가를 자동으로 바꾸지 않는다. 없는 수수료를 임의로 0으로 잡지 않는다. |
| D05 | 비용과 손익 | 제공된 일별 비용기록을 실적 비용의 기준으로 삼고 월비용계획은 별도 비용으로 더하지 않는다. 새 비용은 사용자가 지정한 귀속 날짜에 반영하며, 재료 입고 대금과 판매 원가를 같은 비용으로 중복 반영하지 않는다. 세금 신고용 확정 이익이 아닌 운영 참고 손익으로 제공한다. | 7월 임차료를 월계획과 일별 기록에서 두 번 잡지 않는다. 입고 대금을 수익성에 반영된 원가와 다시 비용 처리하지 않는다. |
| D06 | 실제 재고와 수정 | 판매에 따른 재료 사용과 입고·폐기를 잔량에 반영한다. 실제 센 수량은 해당 실사 시점의 재고 기준으로 사용한다. 과거 기록을 수정해도 이미 확인한 실제 수량의 의미를 유지한다. | 원두를 실제로 2kg 확인했다면 기록상 추정량과 구별한다. 사용량과 실사조정을 이중으로 반영하지 않는다. |
| D07 | 1차 부족 재료 | 잔량이 없거나 음수인 재료는 부족·확인 대상으로 본다. 양수 잔량만으로 향후 충분하다고 단정하지 않는다. 입고 전 소진 예상과 안전재고 기반 추천은 2차로 둔다. | 우유가 0ml면 확인 대상이다. 500ml가 남았다는 이유만으로 내일까지 충분하다고 표시하지 않는다. |
| D08 | 엑셀·저장·복원 | 동일 기록을 중복 추가하지 않고, 충돌하는 기록을 조용히 덮어쓰지 않는다. 기록은 같은 PC에서 지속 보관하고 사용자가 별도 백업 파일을 보관할 수 있게 한다. 복원은 백업 시점 전체 상태로 되돌리는 용도로 하며 기존 자료와 임의로 합치지 않는다. | 같은 판매 양식을 두 번 가져와도 매출이 두 배가 되지 않는다. 백업 복원 시 판매·비용·재고와 관련 기준이 함께 복구된다. |
| D09 | 기간과 마감 | 일·월은 달력 기준, 2차 주간은 월요일 시작, 분기·반기·연간은 1월 시작 달력 기준을 사용한다. 실적은 기록 기준일과 마감 범위를 구별한다. | 2026년 실적에 9월 18일까지 자료만 있으면 그 범위를 알린다. 미래 미마감 날짜는 판매 0으로 보지 않는다. |
| D10 | 2차 예상 손익·발주량 | 우선 조회 중인 달의 월말 예상 손익과 다음 입고까지 부족할 재료·발주 참고량을 대상으로 한다. 실적과 예상, 예상의 기준 시점을 구별하고 주문 여부는 운영자가 판단한다. | 월 중간에 이번 달 손익과 다음 입고 전 우유 부족 가능성을 참고한다. 예측 방법과 정확도는 아직 확정하지 않는다. |

저장은 사용자가 저장한 기록을 다시 사용할 수 있다는 요구사항이다. 자동 저장 여부, 저장 위치의 구체적인 형태, 복원 전 확인 절차 등은 이 문서에서 정하지 않는다. ‘실제 재고 기록 시점’ 역시 어떤 정보를 구분해야 하는지에 대한 요구사항이며 입력 항목이나 처리 순서를 지정하지 않는다.

## 7. 후속 설계에서 정할 사항

제품 목적과 1차·2차 범위 및 6장의 업무 원칙은 정리했다. 다음 내용은 최초 요청에 따라 이번 PRD에서 결정하지 않는다.

- 원가·수수료·기간 손익·재고·예상 손익·발주량의 구체적인 계산식과 반올림 기준.
- 화면 배치, 시각 디자인, 화면 간 이동과 입력 편의 방식.
- 개발 기술, 저장 기술, 설치·실행·배포 방법.
- 입력 항목의 상세 규칙, 엑셀 중복 식별 방법, 수정·삭제·실사 반영 순서, 복원 절차 등 상세 동작.
- 2차 전망 방법, 기준으로 삼을 과거 기간, 예측 정확도의 검사 기준과 수익성 분류 기준.

설계 결과는 6장의 업무 원칙과 일치해야 한다. 핵심 기능 또는 4시간 범위에 영향을 주는 변경이 생기면 그 차이와 이유를 알리고 범위를 다시 조정한다. 현재 완료된 것은 PRD 작성이며, 프로그램 구현·검사·배포 완료를 의미하지 않는다.
